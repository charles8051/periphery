# Changelog

All notable changes to Periphery are documented in this file.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## Unreleased

### Added
- **`DeviceFilterSpec` — the data form of a `DeviceFilter`** (ADR-0084 D2). One property per criterion, bindable from `IConfiguration` or `System.Text.Json` with no adapter, replayed by `DeviceFilter.Apply(spec)` / `DeviceQuery.Apply(spec)` / `DeviceProfile.FromSpec(spec, name)`. `docs/surface/configuration-driven-tracking.md` previously instructed every consumer to hand-write a DTO plus an if-ladder replaying it; that DTO fell behind the filter in every copy, and the one in the guide was already missing four criteria. A test asserts every `DeviceFilter` criterion has a spec property or a written reason it cannot be data — `Where(...)` is the only exclusion, and it takes a delegate.
  - **`Apply` calls the public criteria methods and nothing else**, because they populate the structured hints providers read to narrow the OS query (`Category` drives the Windows class-GUID pushdown and both enrichment flags; tags populate `RelevantTags`). A hand-rolled predicate replay would match identically and silently turn every spec-built filter into a full-system scan.
  - **Unparseable values throw, naming the property.** This deliberately differs from `WithUsbId(string, string?)`, which answers a bad vendor id with a filter that never matches — defensible at a C# call site, useless when the cause is a typo in a config file and the symptom is a device that never appears. `ProductId` without `VendorId`, and one of `MinWidth`/`MinHeight` without the other, throw for the same reason.
  - **A misspelled or wrongly-cased member throws on the JSON path**, via `JsonUnmappedMemberHandling.Disallow`. The default binds such a document to an empty spec, and an empty spec applied to a filter matches every device on the box. **`IConfiguration` does not honour that attribute** — it is case-insensitive and silently ignores unrecognised keys — so pass `o => o.ErrorOnUnknownConfiguration = true` to `Get<DeviceFilterSpec>()` for the same strictness there. Both halves are documented on the type and pinned by test.
  - **Equality is hand-written** so two specs bound from the same JSON compare equal. The compiler compares `string[]` by reference; ADR-0047 records the same surprise on `DeviceInfo.Tags`. Tags compare as sets, ordinal, with null and empty equal.
- **`DevicePhysicality`** — the data form of `PhysicalOnly()` / `VirtualOnly()`. Named rather than boolean: `"physicality": "Virtual"` reads correctly where `"physical": false` does not, and a named enum can gain a member if the software-device classification is ever refined.

### Fixed
- **`WithAllTags` and `WithAnyTag` captured the caller's array instead of snapshotting it** (ADR-0084 D1). The match predicate outlives the call, so it read whatever the caller's `params` array held at match time rather than at configure time — mutating that array afterwards silently rewrote the filter's criteria. On a `DeviceWatcher` this defeated the lifecycle guard outright: `ThrowIfStarted()` fires when the method is called, so a started watcher whose criteria were supplied as an array variable could be reconfigured out from under the provider that had already captured the filter. Both methods now clone the array. A filter built from a literal argument list was never affected.

### Added
- **`WithIdStartsWith` and `WithContainerId` on `DeviceQuery` and `DeviceWatcher`** (ADR-0084 D1). Both existed on `DeviceFilter` only, so a criterion available to a tracker was unavailable to a query or a watcher. Both are carried by the unenriched device build every provider path uses, so they match symmetrically on arrival and departure.
- **A parity test across the three fluent criteria surfaces** (`CriteriaSurfaceParityTests`). `DeviceFilter`, `DeviceQuery` and `DeviceWatcher` re-declare the same vocabulary by hand and had already drifted. The test asserts every `DeviceFilter` criterion is present on the other two **or** carries a written reason for its absence, and that each forwarder matches on default values, `params`, parameter names and nullability — the four axes a shared interface would *not* have enforced. ADR-0084 D1 originally proposed `IDeviceCriteria<TSelf>` for this; that decision is superseded, and the ADR records what was measured.

### Changed
- **`DeviceWatcher` documents why it has no tag filters.** `WithTag`/`WithAllTags`/`WithAnyTag` are absent by design, not by drift. Tags come from the enrichment pipeline, and the Windows monitor provider seeds its last-known-device cache with the unenriched build — which is the record a removal event carries. A tag-filtered watcher would fire `Appeared` (the startup snapshot enriches) and never fire `Disappeared`, leaking the device as permanently present; Linux and macOS enrich inside their single device build, so the feature would also have been platform-divergent.

### Changed
- **BREAKING: `BufferExhaustionPolicy` has two members and now controls something** (ADR-0082, issue `#322`). `DropOldestQueued` is renamed `LatestWins` and becomes the default; `BlockProducer` becomes `StallProducer`; `DropIncoming` and `AllocateOverflow` are **deleted, not implemented**. All four old values behaved identically, because `CameraSession` hardcoded `FullMode = BoundedChannelFullMode.Wait` and the pool-side switch that distinguished them was unreachable — a producer parked in `WriteAsync` never attempts the next acquisition, so the pool is never asked. `FullMode` now derives from the policy (`LatestWins` → `DropOldest`, `StallProducer` → `Wait`) and the channel is constructed with `itemDropped: OnFrameEvicted`, which disposes the evicted frame so its pooled buffer returns. `DropIncoming` was deleted rather than wired up because it keeps the stalest queued frame while its own doc comment promised low latency, and `AllocateOverflow` defeats the pool to avoid a drop the contract permits. No shims and no `[Obsolete]` markers: a consumer naming a deleted member gets a compile error, and one that never set the policy gets latest-wins instead of a hidden `Wait`, so a slow consumer now sees the newest frame rather than the oldest. `CameraSessionMetrics` gains `ProducerStalls` and `ProducerStallTime`, so its positional constructor takes six arguments.
- **BREAKING: `BufferCount` and `QueueDepth` are one budget, and the session pre-allocates `BufferCount + QueueDepth + 1` buffers** (ADR-0082 D3, issue `#322`). `BufferCount` now means "how many frames the consumer may hold at once" and gets exactly that many; `QueueDepth` reserves its own buffers for frames waiting in the delivery queue. Seeding only `BufferCount` made the two bounds fight: a queued frame held a buffer the consumer was promised, so at `BufferCount: 1` the single buffer sat inside the queued frame, every later frame was refused for want of one, and latest-wins delivered the stalest frame there was — the defect `DropIncoming` was deleted for. The `+ 1` is the producer's spare, and it is the term that makes latest-wins true rather than aspirational: eviction belongs to the channel, the channel only evicts on a write, a write needs a frame, and a frame needs a buffer — so without a spare a consumer holding `BufferCount` leases against a full queue has the copy refused before the write that would have evicted anything, and the stale queued frame survives while every newer frame is dropped. Measured: at `BufferCount: 2, QueueDepth: 1` over 30 frames, the consumer received frame 3 without the spare and frame 30 with it. Evicting before acquiring is the alternative, and it needs the producer to read the channel — the `SingleReader` violation this release deletes (`#323`) — so one buffer is the cheaper answer. The pool can now only run dry when a consumer holds *more* than `BufferCount` frames, which is the one loss no policy can prevent because active leases are never revoked (ADR-0035 Decision 9). Cost: `QueueDepth + 1` more pre-allocated buffers per session — the default pool is 5 rather than 3, about 3 MB at 1080p NV12.
- **A `CameraSession` states that it is lossy.** `CameraSession`'s own documentation now says a consumer must not assume it received every frame, names the two places frames are lost, and says which of them Periphery can count (ADR-0082 D1). The previous text claimed the opposite — "this decoupling prevents slow consumers from causing driver-level frame drops" — which is exactly backwards for a stalled producer.
- **BREAKING: frames are now delivered with tight rows; `Stride` is always `BytesPerRow`** (ADR-0081, issue `#320`). For every plane of every uncompressed frame, `CameraPlane.Stride == CameraFrameLayout.BytesPerRow(format, planeWidth)` and `ContiguousBuffer.Length == CameraFrameLayout.FrameSize(format, width, height)`. Media Foundation rounds the NV12 luma stride up to a 64-byte multiple — measured on three cameras across two vendors, 480→512, 800→832, 848→896, 1440→1472 — and that padding used to reach the consumer while `CameraPlane.Stride` reported the unpadded number for every packed format, so the bytes and the contract disagreed with no exception to say so. The frame pool's copy, which happens on every frame regardless, now removes the padding instead of carrying it. **A consumer that reads `Stride` or sizes anything from `ContiguousBuffer.Length` gets different numbers, with no compiler error to warn it**; one that never reads `Stride` is unaffected. The pool's seed size becomes exact, so a padded mode no longer misses its pooled buffer and allocates a fresh one per frame — up to 2.3 MB at NV12 1440×1080. `IsContiguous` is redefined as "the bytes can be walked as one run" (false only for multiple planes or inter-row padding, unconditionally true for MJPEG) and MJPEG is exempt from the invariant. Also fixes a latent Media Foundation bug: the bottom-up branch flipped exactly `height` rows, so a bottom-up 4:2:0 frame kept the previous frame's chroma; the flip now happens in the pool's copy, over every plane, in the same pass as the de-pad.

### Added
- **`CameraSessionMetrics.ProducerStalls` and `.ProducerStallTime` — the number that was missing** (ADR-0082 D5, issue `#322`). A stalled pipeline and a genuinely slow camera used to be indistinguishable from outside: four days of kiosk logs showed 1080p negotiated at 60 fps, roughly 29.5 fps delivered, and `FramesDropped` summed across every session in the window of **1**. Stall time is capture wall-clock during which the platform's read was not being called, which is where the uncounted upstream loss happens; the count alone cannot be turned into it, and it alone cannot separate one long stall from a thousand short ones, so both are reported. The count is recorded on entry, so a producer parked right now is already in it. Also on the meter as `periphery.camera.producer_stalls` and `periphery.camera.producer_stall_ms`, and in the producer-stopped log line. Timing costs nothing on the fast path: a write that completes synchronously did not stall, so no clock is read.

### Fixed
- **The producer no longer reads the delivery channel** (issue `#323`). `DropOldestQueued`'s eviction branch called `channel.Reader.TryRead` from the producer thread against a channel declared `SingleReader = true`, and it was reachable whenever `QueueDepth >= BufferCount`. Eviction is now the channel's own `itemDropped` callback, so there is one reader and the branch is gone rather than fixed.
- **A `PnpDisableEnable` reset no longer reports success while the driver stack is still reloading — the failure that made healthy Treehopper boards unflashable across a deployed fleet** (issue `#251`, ADR-0060 amendment). `WindowsDeviceReset.DisableEnableAsync` returned the instant `CM_Enable_DevNode` did, so `BootloaderEntryOrchestrator`'s flat 750 ms `SettleAfterReset` was the *only* thing standing between the reset and the next `EnterAsync`. On loaded kiosk hardware the reload outlasted it, the retry's open threw `UsbDeviceNotFoundException`, and **the wasted attempt was charged to the recovery budget** — enough of them and the policy conceded with *"could not put 'Treehopper' into its bootloader after 6 attempt(s) and 4 reset(s)"* on boards that were confirmed healthy hours later. The reset now polls the devnode until it reports started and problem-free (25 ms interval, 2 s bound) before returning, and `IDeviceReset.ResetAsync` documents that as a best-effort obligation: a caller has **no** vantage point of its own here, because this rung fires no watcher edge to wait on. **`ReEnumerates: false` stays** — hardware-measured, not assumed. Across disable/enable cycles a watcher filtered to the device's own LocationPath + serial saw **no edge at all** (0/5), and the device never left enumeration, only flipping `Disabled`/`CM_PROB_DISABLED` → `OK`/`CM_PROB_NONE`. Flipping the flag to `true` looks like the fix and is a trap: with the device continuously enumerated, an identity-filtered wait matches the *still-disabled* node from its own startup snapshot and returns immediately, buying latency and no guarantee. `CM_Get_DevNode_Status` is what works — ~0.07 ms per probe, and it precedes actual WinUSB openability by a tight 14.9–16.2 ms. `SettleAfterReset` is documented as a correlation *bias*, never a readiness gate, so it is not tuned upward to paper over this again. When the readiness poll times out the reset now reports `Failed` rather than `Issued`: ADR-0073's "`Issued` is not a health verdict" licenses reporting success when a rung **cannot** observe the outcome (the ADR-0075 EP0 rescue), but a poll that watched and saw the node not restart is *evidence of non-recovery*, and claiming success on it is the same over-claiming this change removes one level up. The 2 s bound is deliberately two-sided: it clears the 750 ms that failed, but must not overshoot either, because Treehopper is an EFM8 **no-serial family** (shared bootloader id `0x10C4:0xEAC9`) whose reboot → correlate → flash window `FlashAnythingService` gates **one board at a time** — so a stall blocks the box's other boards while the kiosk watcher is racing the kiosk's own claim on a margin measured in seconds.

### Added
- **`CameraDevice.GetControlAsync` — read a control's current value and mode, the missing half of set/reset.** Without it a caller can move a control but cannot record where it was, so "restore what I found" was inexpressible and the best available was "return it to automatic". `CameraControlState` is a *reading* and is deliberately separate from `CameraControlInfo`: that type describes a control's fixed shape and is stable for the life of the device, while this one is true at the moment it was taken and potentially false immediately after, because the whole point of these controls is that the device keeps moving them. Folding them together would have made `GetControlsAsync` — a capability query — do per-control IO and hand back values stale on arrival. `CameraControlMode` (`Unknown` / `Manual` / `Automatic`) is a semantic value, not either platform's encoding: **Media Foundation** carries mode as a flag on the control (`MF_CAMERA_FLAGS_AUTO`/`_MANUAL`, returned alongside the value by `IAMVideoProcAmp::Get`), while **V4L2 has no such flag at all** — automatic behaviour is a *separate companion control* whose sense is not even consistent between controls. `V4L2_CID_AUTO_WHITE_BALANCE`, `V4L2_CID_AUTOGAIN` and `V4L2_CID_FOCUS_AUTO` are booleans where 1 means automatic; `V4L2_CID_EXPOSURE_AUTO` is an enumeration running the *other way* (`AUTO` = **0**, `MANUAL` = 1) with two further priority modes, so reading it as a boolean reports every auto-exposure camera as manual. `Unknown` is a **named gap, never a synonym for manual** (the posture ADR-0068 set for rotation and ADR-0073 D4 for topology): a caller that read it as `Manual` would believe a value is pinned when it may be drifting. A control with no auto companion at all reads as `Manual`, which is a real determination rather than the absence of one.
- **`InMemoryCameraBackend.SetControlState` and `RefuseControlRead`** (ADR-0065). The fake derived mode from `SupportsAutoMode`, which made `CameraControlMode.Unknown` unreachable and left a consumer whose restore logic mishandles it with a green suite, and modelled no driver that answers enumeration but declines a read — the failure mode the Windows unsupported-property branch exists for. Both are now configurable, so the seam models the camera rather than an idealised one.

### Fixed
- **`SetControlAsync` meant two different things per platform, and `GetControlAsync` made it visible.** Media Foundation passes `MF_CAMERA_FLAGS_MANUAL` on every set, taking the control away from the device; V4L2's `SetControlCore` wrote only the value and never touched the auto companion, so on the out-of-box state of essentially every UVC webcam the write either failed with `EBUSY` — which is why the existing error hint already told the caller to *"disable auto first"*, an admission the public API gave them no way to act on — or was overwritten by the device's auto loop on the next frame. V4L2 now switches the companion to manual before writing the value, and `ResetControlAsync` hands the control back to the device afterwards, mirroring Media Foundation's reset-with-`_AUTO`. `V4l2FormatMap.MapModeToAutoValue` is the inverse of `InterpretAutoValue` and a test pins the round trip, because if the two drift apart a Linux write silently stops pinning anything. **BREAKING on Linux**, in two ways a compiler cannot see: a `SetControlAsync` that previously no-opped against an auto loop now takes effect, and `Set`/`Reset`/`Get` now *throw* in cases they previously reported as success or as an absent control. The mode switch is **enforced rather than best-effort** — the first draft wrote the companion best-effort on the theory that a refused switch would surface as `EBUSY` on the value write that followed, which V4L2 drivers are under no obligation to produce; a driver that accepts the write and lets the auto loop overwrite it next frame would have returned a successful `SetControlAsync` over a control the device was still driving. Enforcement reads the companion back before throwing, so a read-only companion or one already at the requested mode still passes, and a `VIDIOC_QUERYCTRL` failure is no longer read as "the device has no such companion" — that collapse silently skipped the enforcement entirely.
- **Media Foundation control reads no longer report a lost camera as one with no such control.** `Get` returning any failure HRESULT was treated as "no reading", which swallowed `E_ACCESSDENIED` and the device-invalidated HRESULTs that a USB blip produces — the exact conditions `ThrowForHr` exists to translate into `CameraDeviceLostException` / `CameraAccessDeniedException`. Only `E_PROP_ID_UNSUPPORTED` now maps to a null reading; everything else is thrown. The read also no longer calls `RequireCameraControl` on a device that exposes only `IAMVideoProcAmp` (common on fixed-lens UVC cameras), which threw — synchronously, out of a `Task`-returning method — where the contract promises null, and it now observes its cancellation token and runs off the caller's thread like its siblings.
- **`SetControlAsync` rounded on Linux and truncated on Windows.** Now rounds on both, so a `Get` → `Set` → `Get` round trip returns the same integer on either platform.
- **`MonitorLayoutEntry.PanelId` — the EDID identity of the panel, and the only signal measured to distinguish a synthetic display from a real one** (ADR-0073). Four separate attempts across two days tried to answer *"is this screen virtual"* from output technology, and measurement falsified each one; ADR-0073 records why that was structural rather than four unlucky mappings. **Windows has no concept of "is there real glass at the end of this"** — an indirect display driver is a driver that *presents* a monitor, and whether photons emerge is outside the OS's model — so output technology, connection kind, and even the adapter devnode are all shared between the real and synthetic cases *by construction*. What does separate them is what the panel **claims to be**: the fleet's `IddSampleDriver` rigs report `LNX0000`, distinct from every real panel measured (`ACR0507`, `SAM7089`, `BNQ7F31`, `ACI24C4`). `MonitorPanelIdentity` (vendor + product, with `PnpId` formatted to match the `DISPLAY\<here>\…` device-path segment so it joins to `DeviceInfo.Id` and to a known-synthetic list without reformatting) comes from the `GET_TARGET_NAME` query `CcdLayout` **already issues** — same struct as `DeviceId` and `OutputTechnology`, **no new interop call**, the fields were simply being read past and dropped. It is documented as a **fingerprint, not a fact**: it works only because that driver's author chose that EDID. This supersedes ADR-0070's premise that EDID could not help — that reasoning ("a dual-rig box's two virtual displays share one baked EDID") was true but answered *disambiguation* (which rig is which) when the question was *classification* (is this one synthetic); conflating them cost four attempts. **Periphery still does not synthesize `IsVirtual`** and now records why permanently (ADR-0073 D1): the verdict is not a function of anything Periphery can observe, so emitting one would launder a fingerprint into an authoritative-looking boolean. Adapter identity (parent devnode — `ROOT\DISPLAY\0000` + `WUDFRd` for IddCx) was measured and is documented but deliberately **not** surfaced here: `MonitorLayout` is a zero-handle read, and the discovery plane already models the device tree, which `DeviceId` joins to. Surfaced by the CLI as a `Panel` column and in `--json`.
- **`MonitorLayoutAvailability.NotMeasured`, at ordinal 0** (ADR-0073 D4, issue `#210`). The enum modelled the two *outcomes* of a topology read but not the *absence* of one, so every consumer with a non-Windows fallback had to assert something it never observed. Both consumers hit this independently within hours and both shipped a comment saying the value they picked was wrong — *"periphery models the two OUTCOMES of a read, not the absence of one"* (one consumer), *"the least-wrong value, not the right one"* (a second consumer). Two independent teams documenting that a library value is inaccurate is the library's defect. `NotMeasured` is the **zero** value so a default-constructed `MonitorLayoutAvailability` asserts the least, where previously `Available = 0` made it the enum's strongest positive claim. Carries the posture ADR-0068 set for rotation: unmeasured is its own state, never a negative result. `MonitorSessionVisibility.Classify` never returns it — it runs only after a read — and a test pins that.

### Changed
- **`DisplayConnectionKind.Virtual` and `MonitorOutputTechnology.IndirectVirtual` no longer claim RDP and VM displays as their examples.** Measured: a live Remote Desktop session display reports `Other`/`Unknown`, and a QEMU VM display reports `Other`/`Unknown`. Both members are retained as the faithful mapping of `INDIRECT_VIRTUAL`, and keeping the indirect pair distinct (ADR-0072) remains correct — folding them would misreport real dock-attached glass — but **no measured source produces either member**, and the docs now say so rather than naming examples that do not hold.

### Documentation
- **Measured: an `IddSampleDriver` virtual display reports `Hdmi`, not `INDIRECT_WIRED` — the premise behind ADR-0070 D2 and ADR-0072 is false, and output technology is not a virtuality signal at all** (ADR-0072 Decision 4, issue `#205`). ADR-0072 named one open item as *"the only thing that can promote it past Proposed"*: whether an IddCx display actually reports `INDIRECT_WIRED`. It was run on a Win10 LTSC 2019 sandbox VM against ge9's `IddSampleDriver` with two always-on virtual monitors, in the console session. Both report **`outputTechnology = Hdmi`**, and the discovery plane reports **`DisplayConnectionKind.Wired` / `DisplayConnector.Hdmi`** — neither `INDIRECT_WIRED` (16) nor `INDIRECT_VIRTUAL` (17) appears anywhere. The driver presents a baked EDID (`DISPLAY\LNX0000\…`, monitor name `Linux FHD`) and Windows classifies the target as a cabled HDMI panel. **`DisplayConnectionKind.Indirect` therefore never fires for these rigs**, and the mapping from output technology to "is there a real panel" is not a function in either direction: a real dock-attached panel can report `INDIRECT_WIRED`, and a synthetic display can report `Hdmi`. **The decision to keep the two indirect technologies distinct still stands and is strengthened** — the rejected fold would have false-positived real DisplayLink panels *and* still missed every fleet rig. ADR-0072's explicitly-recorded conditional ("if Windows emits something else … no worse than before, but does not achieve its stated intent") is exactly what occurred, which is why the outcome is legible rather than a silent wrong belief. New Decision 4 states permanently that `MonitorOutputTechnology` and `DisplayConnectionKind` answer *how* a display is attached and never *whether it is real*; a consumer needing `IsVirtual` must use panel identity (EDID) or deployment inventory. Also measured and worth knowing for any fleet tooling: **display configuration is session-local, so `monitor layout` over SSH reports zero monitors on every Windows box** (SSH lands in session 0, the console is session 1) — the monitor commands must be driven from the console session, e.g. a scheduled task with an Interactive principal. **Extended by a second round on a live RDP session, a live VNC session, and a QEMU VM display:** a Remote Desktop session display reports `Other` / `Unknown`, and a QEMU VM display reports `Other` / `Unknown` — so the `Virtual` member's own documentation, which named *"Remote Desktop session"* and *"virtual machine"* as its examples, was documentation-sourced and is measurably wrong; it is corrected here. VNC attaches to the existing console session and adds no display at all. That makes **four** virtualization mechanisms measured with **none** producing an indirect value: `IndirectWired`, `IndirectVirtual`, `Indirect` and `Virtual` are currently members that nothing observed has ever produced. They are kept as the faithful mapping of the two native values, but no consumer should wait for them to fire. Still unmeasured: whether *anything* reports `INDIRECT_WIRED` — a DisplayLink / USB-C dock driving real glass is the one plausible candidate left.

### Added
- **`MonitorLayout.Availability` — an empty layout now says *why* it is empty, so session-0 blindness stops looking like a headless machine** (issue `#207`). `MonitorLayout.ReadAsync()` returned `{"monitors": []}` in two situations that demand opposite responses: genuinely no displays attached, and *displays are attached and working but this process cannot see them*. Display configuration is session-scoped, so **every Windows service — and every OpenSSH command shell — runs in session 0 and sees an empty topology no matter what is plugged in**. Measured on two boxes: over SSH, `monitor layout` reported zero monitors; the same box at the same moment, driven from the console session, reported two. The old XML doc actively encouraged the mistake, telling callers they could treat `Monitors.IsEmpty` as a safe no-op. `MonitorLayoutAvailability` now distinguishes `Available` / `NoActiveDisplays` / `NotVisibleFromThisSession`, and the doc directs callers to branch on it instead. The classifier is a pure total function (`MonitorSessionVisibility.Classify`) taking the entry count and the session id, so the session-0 case — which otherwise only ever happens inside a service — is unit-tested from an ordinary test run. It deliberately claims blindness **only** for session 0, the one case decidable from the session id alone: the tempting generalisation "any non-console session is blind" is false, because an RDP session has its own display configuration and legitimately sees its own monitors. Detection uses the BCL session id — **not WMI**, which ADR-0009 removed from the Windows provider because `System.Management` is not trim/AOT safe and `winmgmt` is a runtime dependency disabled on exactly the hardened / IoT images this matters for — and it is a single point read, no poll (ADR-0054). The CLI surfaces it in `monitor layout` (both table and `--json`) and **exits 2** when the session cannot see displays, so a fleet smoke check cannot silently record a session-blind read as a true empty topology. **Breaking:** `MonitorLayout` gains a second positional parameter, so its constructor *and* its `Deconstruct` shape change — `new MonitorLayout(monitors)` and any positional deconstruction no longer compile. Permitted under the repo's pre-1.0 stance; the guidance change matters more than the signature, since callers that branch on `Monitors.IsEmpty` still compile while being wrong in a service.
- **`MonitorLayoutEntry.OutputTechnology` — the kind of video output a monitor is attached through, as a platform-neutral `MonitorOutputTechnology` semantic value** (ADR-0070). A monitor's output technology — `Internal` / `Vga` / `Dvi` / `Hdmi` / `DisplayPortExternal` / `DisplayPortEmbedded` / `IndirectWired` / `IndirectVirtual`, with an `Other` fallback — is the only signal the topology carries for *how a screen is attached*: the `DeviceId` carries port identity, not output kind, and a dual-IddSample rig's two displays share one baked EDID so a serial cannot tell them apart. The value was **already read and discarded** — `CcdLayout` issues one `DisplayConfigGetDeviceInfo(GET_TARGET_NAME)` per path for the instance id and friendly name, and the struct it fills also carries `OutputTechnology` — so surfacing it costs **no new interop call**, just a read of a field already populated and a mapping. Modeled exactly like `MonitorOrientation` (ADR-0064): a platform-neutral semantic enum whose numeric values are an opaque serialization contract, with the single Windows translation isolated in the new `CcdOutputTechnology.FromCcd(uint)` (total — unmapped native values, including the raw `OTHER` / `_FORCE_UINT32` sentinels, read as `Other`) so no raw Win32 `uint` reaches the public surface and a future non-Windows backend maps from its own encoding without touching the contract. **`INDIRECT_WIRED` and `INDIRECT_VIRTUAL` are kept as two distinct members, and there is deliberately no single `Virtual` value** (ADR-0070 D2). The requesting consumer asked for them collapsed into one `Virtual` member on the premise that IddCx rigs report `INDIRECT_WIRED`; that was rejected, because `INDIRECT_WIRED` is the general indirect-display path — **DisplayLink adapters and USB-C / Thunderbolt docks drive genuinely physical panels through it**, and Windows does not distinguish those from a synthetic IddCx rig at this layer. Collapsing would therefore report *real glass as virtual*, a false positive on precisely the question such an attribute exists to answer. Whether a given indirect display is synthetic is a deployment-informed judgement, knowable only to the consumer, so Periphery reports the platform fact and declines to guess. A unit test explicitly pins the two members apart, since folding them back together looks like a harmless simplification. It is a **read-only, descriptive** attribute: no apply-side counterpart on `MonitorConfiguration` (Windows exposes no way to set output technology), and it drives no actuation. The `MonitorLayoutEntry` positional constructor changed shape (additive field); `LayoutDiff` / `MonitorLayoutApplier` compare individual fields, never whole-record equality, so apply behaviour is unchanged.

### Changed
- **`DeviceInfo.DisplayConnectionKind` reports the new `DisplayConnectionKind.Indirect` for a DisplayLink / dock / IddCx display, instead of folding it into `Virtual`** (ADR-0072, superseding ADR-0071 Decision 1; issue `#202`). Three changes landed within ~40 minutes, in separate sessions, on one question — what does `DISPLAYCONFIG_OUTPUT_TECHNOLOGY_INDIRECT_WIRED` (16) *mean*? — and disagreed: the discovery plane folded it into `Virtual`, the control plane kept it distinct, and an ADR recorded the fold as cross-plane parity while citing a decision that had already been reversed. The fold is the defect. **`INDIRECT_WIRED` is not an IddCx marker — it is the general indirect-display path, and DisplayLink adapters and USB-C / Thunderbolt docks drive genuinely physical monitors through it**, alongside synthetic rigs like IddSampleDriver; Windows does not distinguish them at this layer. So both prior answers were assertions the code cannot support: `Wired` (before `#200`) claims a cable about a synthetic rig, and `Virtual` (`#200`) claims *no physical panel* about a real monitor on a dock — a false positive on exactly the question a "virtual?" attribute exists to answer. Trading one false positive for another is not a fix, so the enum gains a member that asserts only what is known: `Indirect` = "presented by an indirect display driver; whether a panel is attached is not knowable at this layer." `INDIRECT_VIRTUAL` still maps to `Virtual`, whose documentation now says explicitly that it means **no physical panel** (RDP, VM). This is ADR-0071 Decision 2's own rule applied one level up — that rule is **unaffected and still governs** the full enumeration and the honest `_ => Unknown` default; it prefers adding a faithful member over folding into a neighbour, which is exactly what this does. Both planes now keep the pair distinct (the control plane's `MonitorOutputTechnology` has `IndirectWired` / `IndirectVirtual`), with tests pinning them apart on each side, since refolding them reads as a harmless simplification. Adding a public enum member is free here: no known consumer reads `DisplayConnectionKind` yet. Still unmeasured across all four changes: that IddCx actually reports `INDIRECT_WIRED` — a live four-panel read on the dev box returned only `DISPLAYPORT_EXTERNAL`×2, `DVI` and `HDMI`, with no indirect display attached. `Indirect` is deliberately robust to that gap, where either fold would have baked the unverified claim into a boolean.

### Documentation
- **ADR-0071 records why an indirect display is `Virtual` on both planes, and the mapping rule that keeps it that way.** *(Decision 1 superseded by ADR-0072 — see **Changed** above; Decision 2, the mapping rule, stands.)* It resolves the divergence ADR-0070 Decision 2 deferred (the discovery plane read IddCx rigs as `Wired`; the control plane read them as `Virtual`), and generalises the fix into a rule: a translation from an **open** native enumeration into a value Periphery *reports* must name every value the platform defines and default to the target type's unknown sentinel, never to a substantive one — `_ => Wired` was not a default but an assertion about hardware the code failed to recognise. The rule is deliberately conditional: `DisplayGeometry.FromCcdRotation`'s `_ => Landscape` stays, because CCD rotation is a **closed** set, `DisplayOrientation` has no unknown member, and the value is consumed as arithmetic rather than reported. ADR-0071 also affirms ADR-0070 Decision 4 — the two planes keep separate types and merely agree on virtuality — and documents the tier's real reach: `DisplayConnectionKind` / `DisplayPhysicalConnector` have exactly one producer, the Windows CCD enricher, and are `null` on Linux and macOS, where `null` means **unmeasured**, never "not virtual".
- **The `DisplayConnectionKind`, `DisplayConnector`, and `DisplayUsageKind` XML docs no longer name a data source that does not exist.** All three claimed to be "Sourced from `Windows.Devices.Display.DisplayMonitor.*`" — a WinRT API whose enricher was deleted in `47c7eb3` under ADR-0018, which replaced it with Win32 DisplayConfig and removed the Windows TFMs outright, so the projection could not compile in this repo today. They now name the CCD `DISPLAYCONFIG_VIDEO_OUTPUT_TECHNOLOGY` source and state the non-Windows `null`. `DisplayUsageKind` additionally documents that it has **no producer on any platform** (ADR-0018 NEG-002) and is retained as a modelled contract slot rather than deleted.

### Fixed
- **`treehopper-flash reboot` no longer reports `NO EFFECT` for a reset that worked — and wire opcode `0x0C` is not an unreliable re-enumeration trigger, which is what the old detector made it look like** (issue `#230`). The verb polled `TreehopperBoard.EnumerateAsync` every 500 ms while the board is off the bus for **~230 ms**, so a working reset landed inside one sampling interval and was reported as hardware that did not respond. Two detection strategies existed in this codebase and the verb had picked the weak one: core's `WindowsDeviceMonitorProvider` is event-driven (`CM_Register_Notification`) and cannot miss a transient, and `periphery devices watch` — standing right next to this verb — captured the whole disappear/activate pair the poll never saw. The verb now **subscribes to that same stream** (`Devices.Watch()`, filtered to the one board) **before** writing `0x0C`, and **reports the measured absence**: `OK - left the USB bus 14 ms after the write, back at 245 ms (absent ~230 ms)`. Both edges are printed, not just the gap, because they are notification-arrival stamps: under load the two can arrive late and bunched, which compresses the gap without moving the verdict, and printing both makes that visible instead of silent. Measured on two boards and independently corroborated by `DEVPKEY_Device_LastArrivalDate` moving across the same reset. The alternative — comparing `LastArrivalDate` before and after — was rejected: it proves a re-arrival but carries no drop edge, so it cannot report a gap at all, and it is Windows-only where the watcher works wherever a monitor provider does. **The negative verdict is now worth trusting and says why** (*"watched live via OS device notifications, so a drop of any length would have been seen"*), where the old one quoted its own poll interval as a caveat. Detection is a pure fold — `RebootObservation.Observe` over timestamped `RebootSignal` values, with `BoardReboot.Classify` / `Summarize` (ADR-0052 shape) — so the ~230 ms transient, the initial snapshot's activation of a still-present board, and the duplicate edges one physical transition produces (deactivate + remove, appear + activate) are all unit-tested with no hardware. **A second, independent defect in the same detector is fixed alongside it:** the deleted `Present()` predicate compared serial numbers with `==` — ordinal, because `DeviceInfo.SerialNumber` is a raw `string?` rather than a typed `DeviceId` — and the serial is exactly the token that re-cases, since the Windows provider derives it from the last segment of the instance id and the Treehopper firmware's serial alphabet spans `0-9`, `A-Z` **and** `a-z`. That produced a *different* false verdict from the polling one — `WARNING - dropped but did not return`, plus a non-zero exit — for a board that had come back. Identity is now matched **case-insensitively** throughout `BoardReboot.IsSameBoard`, with tests that fail if either comparison regresses to ordinal (`#231`). The corresponding "not a reliable re-enumeration trigger" claim is corrected in `BoardRenamer` and `BoardRename` too; the separate and still-true claim that `0x0C` **cannot rescue a wedged board** — it travels over the same wedged endpoint, which is the motivation for the EP0 rescue in `#227` — is untouched.
- **An IddCx indirect display is now reported as `DisplayConnectionKind.Virtual` on `DeviceInfo`, not `Wired` — and an output technology this build does not recognise is reported as `Unknown` rather than asserted to be a cable.** `WindowsDisplayConfigEnricher.MapConnectionKind` mapped only `DISPLAYCONFIG_OUTPUT_TECHNOLOGY_INDIRECT_VIRTUAL` (17) to `Virtual` and let everything else fall through to `Wired` — but an IddCx / IddSampleDriver indirect display (the fleet's virtual-monitor rigs) reports `INDIRECT_WIRED` (16), which was not even a named constant, so those software-presented displays were misclassified as physically cabled. Both indirect technologies now fold into `Virtual` here. **Note the two planes deliberately disagree, and this fold is under review:** the control plane's `MonitorOutputTechnology` (ADR-0070 D2) keeps `IndirectWired` and `IndirectVirtual` as *distinct* members, because `INDIRECT_WIRED` is also how DisplayLink adapters and USB-C / Thunderbolt docks drive genuinely **physical** panels — so folding reports real glass as virtual. This entry's original claim that it matched the control plane no longer holds; see `#202`. **The default `_ => Wired` arm was the underlying defect** — it is what let an unnamed value be asserted to be cabled in the first place, and it would have done the same to the next technology Microsoft adds — so `DISPLAYCONFIG_VIDEO_OUTPUT_TECHNOLOGY` is now enumerated in full (`SVIDEO`, `COMPOSITE_VIDEO`, `COMPONENT_VIDEO`, `D_JPN`, `UDI_EXTERNAL`, `UDI_EMBEDDED`, `SDTVDONGLE`, `DISPLAYPORT_USB_TUNNEL`) and the default answers `Unknown`. Enumerating the enum is what makes that default honest: flipping it alone would have demoted genuinely-cabled outputs such as SDI and S-Video to `Unknown`. `UDI_EMBEDDED` also joins the `Internal` arm, per the SDK's direction to prefer the "embedded" values over the redundant `INTERNAL`. Alongside it `MapConnector` now produces **`DisplayConnector.AnalogTv`**, a public enum member no input could previously reach — the whole analogue-television family (S-Video, composite, component, Japanese D-terminal, SDTV dongle) fell through to `Unknown` — and maps `DISPLAYPORT_USB_TUNNEL` to `DisplayPort`. No consumer read either surface yet, so nothing depended on the wrong classification; both mappers are now `internal` and unit-tested with no display hardware, including the default arm.

## 3.0.0 - 2026-07-24

### Added
- **Windows now raises `DevicePropertyChanged` for the monitor DisplayConfig tier — an event that had never fired on Windows before** (ADR-0066, amending ADR-0054 D2 under D3's provision). Every consumer of `DeviceWatcher` / `DeviceTracker` on Windows will start receiving monitor property deltas it previously could not receive; nothing needs to change to get them, and the tracker already re-stamps them via `ApplyPropertyChanged`. This closes three distinct holes. `DeviceInfo`'s monitor identity fields (`MonitorName`, `DisplayResolution`, `DisplayBounds`, connector kind) are not device-node properties — they come from a whole-topology `QueryDisplayConfig(QDC_ONLY_ACTIVE_PATHS)` batch keyed by PnP instance id that the provider ran **only during full enumeration** — so a **freshly hotplugged monitor arrived with all of them `null` and never recovered**, a **re-appearing monitor's bare arrival payload overwrote a good boot snapshot**, and a **mode / rotation / resolution change on an already-attached panel produced no event at all**. `WindowsDeviceMonitorProvider` now owns a `WindowsDisplayChangeSink`: a hidden top-level window pumping `WM_DISPLAYCHANGE` on its own background thread. On each display change — and on a monitor devnode arrival, coalesced onto the same queue so a genuinely-new panel is covered regardless of arrival-vs-topology ordering — the provider re-runs `WindowsDisplayConfigEnricher` over its cached `Monitor`-category snapshots and raises `DevicePropertyChanged` with the `(previous → enriched)` delta; arrival and instance-started payloads additionally merge the whole monitor tier forward from cache before `DeviceAppeared` / `DeviceActivated`, so a re-appearance is never a bare clobber. This is not polling and not a tree scan: it fires only on the OS's own topology-settled edge, the `WndProc` posts a private message and returns (the `SendMessage`-delivered broadcast is never blocked), and the enricher's EDID registry reads run outside the provider cache lock. **No contract change** — `DevicePropertyChanged` is already declared on `IDeviceMonitorProvider` and raised by the Linux/macOS providers; Windows now honours it for this tier. Two limits worth knowing: a message-only window cannot be used (the broadcast only reaches top-level windows), so the hidden window is visible to `EnumWindows`; and in session 0 (a service with no interactive desktop) it does not receive the console session's broadcast, so the refresh is inert there and the provider degrades to its previous behaviour rather than failing. The driver was a downstream window manager, which resolves a role→`Screen` binding by `MonitorName` off Periphery's enriched `DeviceInfo` rather than a Win32 message it pumps itself.

### Changed
- **`MonitorLayoutEntry.DeviceId` and `MonitorConfiguration.DeviceId` are `DeviceId` values, not `string`** (issue `#190`). The two were documented — and specified by ADR-0059 D2 — as the same identity core surfaces as `DeviceInfo.Id`, *"so layout entries join to `DeviceInfo` … directly"*. They did not join: the layout reader takes the id from the CCD `monitorDevicePath` transform (lower-case) while core's `DeviceInfo.Id` comes from the device-instance enumeration path (upper-case), so on a four-monitor box an **ordinal join matched 0 of 4**. It stayed invisible because every comparison inside `Periphery.Monitor` already worked around it with an explicit `OrdinalIgnoreCase` — but the raw `string` was exported, so a downstream consumer joining the two planes got nothing, silently. Typing both as `DeviceId` (whose equality and hashing are `OrdinalIgnoreCase`) makes the join correct by construction. **Source-compatible for most callers** — `DeviceId` converts implicitly to and from `string` — but it is a binary-breaking signature change, and code that relies on the property *being* a `string` (LINQ projections to `IEnumerable<string>`, pattern matches) needs a `.Value`. Normalising the case instead was implemented and measured, then rejected: `CM_Get_Device_Interface_Property(DEVPKEY_Device_InstanceId)` returns the *same* lower-case string, and Windows reports one instance id in different case from different APIs anyway — core's own snapshot and change-notification paths disagree for the same reason, which is why `DeviceId` exists.

### Fixed
- **A rotated monitor no longer reports a geometrically impossible `DisplayBounds`, and a pure rotation now raises `DevicePropertyChanged`** (ADR-0068, issue `#163`). `DeviceInfo.DisplayBounds` was assembled straight out of `DISPLAYCONFIG_SOURCE_MODE`, mixing two frames of reference: the **position** is the origin Windows laid the panel out at, computed from its *rotated* footprint, while **width/height** describe the source surface, which rotation does *not* transpose. A 1920×1080 panel rotated to portrait left of the primary reported `1920x1080 @ (-1080,0)` — a rectangle running to +840 that overlaps its neighbour at x=0, describing no real desktop layout (a windowing toolkit reported `1080x1920 @ (-1080,0)` for the same screen). Worse, rotating the **primary** panel at (0,0) — where the origin cannot move — left the snapshot byte-identical, so `DeviceInfoDiff` found nothing changed and **no event was raised at all**; with no rotation property on `DeviceInfo`, the change was simply unobservable. Both are fixed: `DisplayBounds` is now the panel's real on-desktop footprint (size transposed for a 90°/270° rotation, position untouched, matching `GetMonitorInfo`), and rotation is surfaced as a first-class **`DeviceInfo.DisplayOrientation`** (`Landscape`/`Portrait`/`LandscapeFlipped`/`PortraitFlipped`, `null` when unmeasured) populated from the `DISPLAYCONFIG_PATH_TARGET_INFO.rotation` that was already being read and discarded — and diffed, so a rotation always raises `DevicePropertyChanged` even when the origin and footprint are both unchanged. The reconciliation is a pure, total core (`DisplayGeometry.FromCcdRotation` / `DesktopBounds` — no IO, no OS call), so the arithmetic that was wrong is exhaustively unit-testable with no display attached. `DisplayOrientation` is deliberately a separate type from the `Periphery.Monitor` control plane's `MonitorOrientation` (core cannot depend on the optional extension) and is kept exactly parallel to it — same members, same ordinals.
- **A consumer that applies a display layout from a monitor event handler no longer hangs Periphery's display-change pump** (ADR-0066 Decision 2a, rewritten; issue `#153`). The first implementation of the monitor event-ordering rule used a provider lock (`_monitorEventGate`) held **across the raising** of `DeviceAppeared` / `DeviceActivated` / `DevicePropertyChanged`. That fan-out is synchronous into consumer code — `DeviceWatcher` → `DeviceTracker` → `StateChanged` / observers all run on the raising thread — so an internal lock ended up wrapping arbitrary consumer handlers. The stall is the station agent's actual flow: a handler that calls `SetDisplayConfig` runs on the cfgmgr32 callback thread holding the gate, Windows broadcasts `WM_DISPLAYCHANGE` by `SendMessage` to every top-level window including the sink's, only the pump thread services it, and the pump thread is blocked on that gate — so the broadcast stalls until Windows declares the window hung. The milder variant is worse to diagnose: a handler that merely blocks on the refresh path wedges the pump thread for the process lifetime and display refreshes silently stop. Mutual exclusion was standing in for an ordering constraint, so the constraint is now recorded as **data**: a pure `MonitorAnnouncementLedger` tracks, per monitor id, whether its appearance has been raised and whether a publish is in flight (a depth, not a flag — one plug publishes the same monitor twice concurrently, from the interface-arrival and instance-started callbacks on different threads), guarded by the existing cache lock, which never spans foreign code. A refresh **skips an ineligible monitor entirely** — neither raising *nor writing back*; skipping the write-back is the load-bearing half, since enriching the cache without emitting is exactly how enrichment used to get lost — and the in-flight publish's trailing refresh request (in a `finally`, so a throwing handler cannot strand a monitor) re-drives it. **Every event is now raised with no provider lock held.** Dropping the gate also stops serializing monitor arrivals against each other, which was a side effect rather than a goal, and restores the behaviour of the non-monitor path in the same provider and of the Linux/macOS providers.
- **The display-change sink can no longer show up in alt-tab or block a host's startup indefinitely** (`#152`) — two hardening fixes raised by a downstream kiosk consumer reviewing the refresh hook before pinning to it. The hidden window is now created `WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE`: it could never become visible anyway (zero-size, no `WS_VISIBLE`, never shown), but that rested on our convention rather than an OS rule; the bits make the shell exclude it from the taskbar and the alt-tab switcher and stop it ever taking activation, and neither affects delivery of the `WM_DISPLAYCHANGE` broadcast. And `Start()`'s readiness wait is now **bounded (5s)**, with the two P/Invokes that ran before the pump thread's `try` moved inside it — previously anything throwing before that `try` skipped the `finally`'s readiness signal and left `Start()`, and therefore `DeviceWatcher.StartAsync`, blocked **forever**. Vanishingly unlikely for those two calls, but it was an unbounded wait on an embedding host's startup path, and a kiosk must never fail to boot because a display-notification window misbehaved. On timeout the sink is treated as unavailable and the provider degrades to no display refresh hook, matching the existing window-creation-failure path.
- **`Periphery.Camera.Testing` can no longer be silently paired with a `Periphery.Camera` it is binary-incompatible with.** The package reaches into `Periphery.Camera`'s internals via `InternalsVisibleTo`, so the two assemblies must be the same build — but it packed a *minimum*-version dependency (`2.2.1`, meaning `>=`). A consumer who let the test package lag while `Periphery.Camera` moved forward got a clean restore and then a `TypeLoadException` / `MissingMethodException` **inside their own test run**, the worst possible place for it, and a downstream kiosk's test suite is already a live consumer. It now emits an exact range (`[2.2.1]`), so the mismatch fails at restore with a comprehensible message. ADR-0065 records the general rule: an internals-bound support package is version-locked to its host by construction.
- **The camera test seam no longer masks the lifecycle bugs it exists to catch.** `InMemoryCameraBackend.OpenAsync` used to *revive* a disposed instance, which existed solely to prop up the single-instance `CameraTestScope.Install(backend)` overload across the session builder's snapshot+capture double open — a usage the docs already steered away from. Removed: a disposed backend now stays disposed, matching the real Media Foundation and V4L2 backends, so a consumer's use-after-dispose surfaces instead of silently working. The `IsOpen` / `IsCapturing` / `IsDisposed` observation properties are now `Volatile` reads (they are written on the producer thread and polled from the test thread), and `CameraTestScope.Dispose`'s documentation now states plainly that out-of-order disposal cannot fully unwind a single global slot rather than implying it can.
- **The display-change sink's cross-thread handles are properly fenced** (`#154` part 1). `_window`, `_pumpThreadId`, and `_pumpThread` are written on the pump thread and read from arbitrary callers, ordered only by `Start()`'s readiness wait — which is deliberately **bounded**, so on the timeout path a caller proceeded with no memory fence at all and could read a stale handle indefinitely. Every cross-thread access now goes through `Volatile.Read`/`Volatile.Write`. Unobserved in the field; found by review.
- **A release can no longer silently ship an incomplete package family** (`#132`). `publish.yml` relied on incremental `dotnet pack` reusing whatever `.nupkg` files the runner's working directory happened to carry — on `v2.0.0-alpha.1` the publish job ran 33 seconds and only four projects actually logged a pack. It worked that time by luck. The build now runs `--no-incremental`, `packages/` is wiped before packing so a stale artifact from an earlier tag cannot be re-pushed, and a completeness gate **derives** the expected package set from every `IsPackable` project in the solution and fails the release loudly if any is missing. Because it is derived, adding a package extends the gate automatically — there is no count to remember to bump.
- **A green test run can no longer block a package publish.** The `v2.2.1-alpha.1` release published nothing: both test jobs ran build and test to success and then failed on "Upload test results" because the account-wide GitHub Actions artifact storage quota was exhausted — and since `publish` declares `needs: [test-linux, test-windows]`, it was skipped and no packages reached the private feed. The `.trx` artifact is a diagnostic convenience that should never gate a publish or red-X an otherwise green run, so all five upload steps (`publish.yml` ×2, `linux-ci.yml` ×2, `build.yml` ×1) are now `continue-on-error: true`, keeping `if: always()` so the upload is still attempted. Not specific to the quota — any transient artifact-service failure had the same effect.
- **`Periphery.Examples.Sandbox` is no longer packed and pushed to the package feed** (issue `#173`). Every other project under `examples/` sets `<IsPackable>false</IsPackable>`; Sandbox was the only one that did not, so every release published a `Periphery.Examples.Sandbox.<version>.nupkg` — a scratch `OutputType=Exe` example, shipped as if it were part of the library family. The reason it went unnoticed is a **stale comment in `src/Directory.Build.props`**, corrected here: it claimed that test, benchmark, and example projects "live OUTSIDE src/ and so do not pick up this file — they remain unpackable by default". Not picking up that file only means no on-build local-feed pack. MSBuild's own default is `IsPackable=true`, so a project outside `src/` is packable **unless it opts out explicitly** — which all 16 test projects and the benchmark project do, and which Sandbox did not. `dotnet pack Periphery.slnx` now produces 16 packages, all from `src/`. Versions already pushed to the private feed are unaffected and need delisting separately.

### Internal
- The three hardware provider contract tests that compared two *live* enumerations of the machine (`CategoryFilter_PushDownNeverOmitsMatchingDevices` and two siblings) moved to the `Integration` tier (`#159`). Any device churn between the two enumerations — a hub re-enumerating, a composite device settling — failed them, and they sat in the tier that gates PRs *and releases*. The push-down property itself is unaffected: `FakeProviderContractTests` already exercises it against a seeded dataset in the gate tier on every platform; what moved is only the part that cannot be de-raced without real hardware.
- The `Codex PR Review` workflow was removed. It had failed on **every PR since it was enabled** (10/10 runs over a month) because it referenced a reusable workflow that does not exist on the target repo's default branch, so the "wait for automated review" convention was gated on a check that could never pass. Peanut Gallery (`#162`) is the working reviewer.

### Added
- **`Periphery.Camera.Testing` — a new published package that lets consumers test `CameraSession`-wrapping code with no camera attached** (ADR-0065). Code that *wraps* a `CameraSession` — opens it, runs its own capture pump around `CaptureAsync`, and handles `CameraTimeoutException`, faults, teardown and reconnect — previously had no hardware-free way to exercise that pump: the public construction paths (`CameraSession.OpenAsync`, `CameraSession.For(device).OpenAsync()`) go straight to the OS capture stack, `CameraSession` is sealed with an internal constructor, and the scriptable fake Periphery's own suite uses sits behind `InternalsVisibleTo`. The package ships **`InMemoryCameraBackend`** — a scriptable, faultable in-memory capture backend that reproduces the failure modes real drivers actually exhibit (`FaultOnOpen`, `FaultOnNextRead`, `HangOnRead`, `MaxFrames`, `FrameDelay`, `OverridePixelFormat`) and reports what the code under test did (`IsOpen`, `IsCapturing`, `FrameCounter`, `ReadHangReached`) — plus two ways to get it in front of your code: **`CameraTestScope`** (redirects the internal `CameraDevice.BackendFactory` for the scope's lifetime, for code that opens from a `DeviceInfo` itself) and **`CameraTestHarness`** (constructs a `CameraDevice`/`CameraSession` directly over the fake, no global state, for code handed an already-open session). Pairing `HangOnRead` with `FakeTimeProvider` (ADR-0052) drives the frame timeout deterministically — which is the incident that motivated the package: on a deployed kiosk a wedged UVC stream (`CameraTimeoutException`, device still enumerated) left capture dead for ~15h and orphaned the session's producer task, and the fix's IO shell (pump-`finally` session disposal, cancellation stop) could not be tested from outside Periphery at all. **The platform I/O contract stays internal:** `InMemoryCameraBackend` implements `ICameraBackend` *explicitly*, so `ICameraBackend` and `RawCameraFrame` remain off the public surface and free to evolve (ADR-0065 rejected making them public precisely to keep that design space open); only the configuration/observation API is public. Periphery's own camera suite now consumes the package, so there is one fake, not two. Caveat: `CameraTestScope`'s redirect is process-global mutable state — serialize tests that use it into a single non-parallel collection, or use `CameraTestHarness`, which needs no redirect. Publishes alongside `Periphery.Camera` and is **version-locked to it** — because it binds to `Periphery.Camera`'s internals, the package declares an exact NuGet range (`[x.y.z]`, not `>=`), so a mismatched pair fails at restore rather than as a `TypeLoadException` inside your test run. The first consumer is a downstream kiosk's test suite.
- **`MonitorLayoutEntry.DesktopSize`** (a new `DisplaySize` value) — the width × height the monitor actually occupies on the virtual desktop, i.e. `CurrentMode` reframed by `Orientation` through the existing `OrientationMath.Reframe`. Derived on read, never stored, so it cannot drift from the mode it is computed from. Consumers previously re-derived the desktop footprint by hand and **disagreed with each other** — the "-312 vs -56" monitor-position bug and a transposed remote-view crop both trace to that guesswork. Layout and position consumers should read `DesktopSize` and stop swapping width/height themselves; see the `CurrentMode` frame pin under **Changed**, which is the other half of this.
- **The Treehopper firmware updater now takes a `.hex` file directly, with a content-verified brick-guard.** `TreehopperFirmwareUpdate.ReflashFromFileAsync(path)`, the CLI `--file`, and the GUI file picker accept either a `.hex` (Intel HEX) or `.tfi`/`.efm8` (boot records): the format is inferred from the extension and **verified against the file content** before any device IO — a `.hex` is converted to boot records in-process (no external `hex2boot`), a boot-record file is replayed as-is, and a file whose content does not match its extension (e.g. Intel HEX text in a `.tfi`) is **refused**, not flashed. No `--hex` flag — the extension is the declared intent, the content is the check. The core is a pure, total `Efm8FirmwareImage.ToBootRecords(content, fileName, options)` (sniff: `:`-leading = HEX, `$`-leading = boot records, then a full parse). Defense in depth: `TreehopperFirmwareUpdate.ReflashAsync(Stream)` now parses the records **before** rebooting the board, so even a direct caller that passes non-records is rejected while the application is still running (the board is never rebooted). Every refusal happens on the file bytes, so the worst case is "nothing happened — fix the file." Supersedes the reflash ADR with Decision 12.
- **`Efm8BootRecordGenerator` — in-house Intel HEX → EFM8 boot-record conversion (a pure `hex2boot` replacement)** in **`Periphery.Bootloader.Efm8.Usb`** — that is the id to reference, and the only one that will be published; the work landed while the package was still called `Periphery.Efm8Bootloader`, an id now retired (see the rename under **Changed**). Converts an Intel HEX firmware image to the `$`-framed AN945 boot-record stream the bootloader uploader replays, so the build → flash pipeline no longer needs the external SiLabs `hex2boot` tool (a Python script + the `intelhex` package). `IntelHexImage.Parse` is a pure, total Intel HEX parser (data / EOF / extended-address records, checksum-verified) — since relocated to the shared `Periphery.Firmware` package, see **Added**; `Efm8BootRecordGenerator.FromIntelHex(hexText, Efm8BootOptions.Ub1)` returns the boot-record `byte[]`, and `Efm8BootOptions` mirrors the `hex2boot` flags (`-m` map, `-b` bank, `-e` erase mode, ids, lock, wait). A faithful, pure (ADR-0052) port of the recovered, byte-verified `hex2boot.py`, with the **brick-safety preserved**: the reset-vector byte is written **last** (address 0 blanked to 0xFF for the write+verify pass, the real byte emitted as the final Write before RunApp), a **Lock (0x35) record is never emitted** (default), and writes stay within the part's app region. Pinned to the reference by a **golden-file test** (byte-for-byte against real `hex2boot` output for `Assets/synthetic.hex`), and additionally cross-checked byte-for-byte against real `hex2boot.py` on the real ~15 KB multi-page Treehopper firmware. Supersedes the reflash ADR's Decision 3 ("input must come from hex2boot"); the uploader stays replay-only.
- **`Periphery.Firmware` — a new published package holding one firmware-image layer for every flasher to share** (ADR-0061 DEC-003). Periphery could already *discover* hardware and speak USB / HID to it; what it could not do was turn a build artifact into bytes a bootloader will accept. This is that layer, and it is deliberately IO-free and BCL-only. `FirmwareImage` is a sparse address→bytes model built from Intel HEX (`FromIntelHex`), a raw `.bin` plus a load-time base address, or a GCC/Clang ELF (`FromElf`, reading `PT_LOAD` program headers at `p_paddr` — the load address the bytes are written to, not the `p_vaddr` the program runs at — and only `p_filesz` bytes, so the `.bss` tail is never flashed; this matches `objcopy -O binary`, OpenOCD and pyOCD). `FirmwarePayload` is the closed union a programmer actually consumes — `MemoryImage(FirmwareImage) | PackagedBlob(format, bytes)` — so a family whose firmware never reduces to addressed segments (EFM8's AN945 boot records) implements the same `IFirmwareProgrammer` as one whose firmware does. `IntelHexImage` and `IntelHexFormatException` moved here out of the EFM8 bootloader package: one parser, not one per family. **Every load path is a brick-guard, not a convenience** — the format is taken from the file extension and then *verified against the file's own bytes*, so a `.hex` mislabelled `.bin` is refused rather than written as raw data at the base address, and an ELF renamed `.bin` (which would otherwise flash its own headers over the reset vector) is refused on the `\x7FELF` magic. Two real defects were found and fixed while building it, both before any of this reached the feed: a caller-supplied `FlashOptions.BaseAddress` collapsed every segment of a multi-segment HEX onto one address, so it is gone — the image always carries absolute addresses now, the planner trusts each segment's own, and a raw `.bin`'s base is supplied at load time instead; and adjacent ELF `PT_LOAD` segments are coalesced into one aligned run, because GCC splits `.text` and `.data` into separate contiguous segments and writing `.data` from its own unaligned LMA (e.g. `0x0800C16C`) mis-lands on an STM32, whose flash is programmed in 64-bit doublewords — that image verified wrong at exactly that byte on real hardware. DfuSe `.dfu` is a named gap that throws rather than half-working.
- **`Periphery.Bootloader` — a new published package: the contract every firmware flasher implements, plus the "wake the device into its bootloader first" orchestration that every device used to hand-roll** (ADR-0061 DEC-003, ADR-0063). Two halves. The **flashing contract** — `IFirmwareProgrammer` (`IdentifyAsync` / `FlashAsync` / `LeaveAsync`, with an `AcceptedFormats` gate so a programmer refuses a format it cannot write *before* any byte reaches the device), `IBootloaderProvider` + `BootloaderRegistry` ("which client handles this discovered device"), `FlashOptions` / `FlashProgress` / `FlashResult` / `DeviceIdentity` — was deliberately not invented up front; it graduated only once two independent flashers (EFM8 over HID, STM32 over USB DFU) had proven the shape. The **bootloader-entry** half addresses the case that is actually typical: a device spends its life running application firmware and has to be told, in its own application protocol, to reboot into its bootloader, after which it *re-enumerates under a different USB identity*. `IBootloaderEntry` is the device-specific sliver of that (`Name`, `CanEnter`, `ExpectedBootloader` as a `DeviceFilter`, `EnterAsync` — for Treehopper, about fifteen lines wrapping a command the board API already had); everything hard is shared once in `BootloaderEntryOrchestrator`: enter → wait for the expected bootloader → safety-gate → flash → optionally wait for the application to return. The wait is **watcher-driven off `DeviceWatcher`, not a poll loop**, and the correlation is a pure, total `DeviceWaitState` advanced by appeared/disappeared events plus one timeout signal — no IO, no clock — so the genuinely hard question ("which re-enumerated device is *mine*?") is unit-testable with no hardware: exact serial correlation where the identity survives the mode switch, first-appearance debounce where it cannot (every EFM8 device presents as `0x10C4:0xEAC9`, so no-serial families are processed one at a time). The **safety gate** is the generalization of Treehopper's per-device `VerifyIsBootloader`: the orchestrator refuses to open or write to anything not matching `ExpectedBootloader`, so device-specific code never gets the opportunity to flash the wrong board. `IFirmwareConverter` + `FirmwareConverterRegistry` bridge a loaded format to one the programmer accepts (Intel HEX → EFM8 boot records, so a `.hex` flashes a Treehopper end to end), and `BootloaderEntryPhase` reports `Entering` / `WaitingForBootloader` so a front-end can render the reboot-and-wait that precedes the flash. One thing to *not* expect from this: there is still no serial transport. ADR-0062 decides its shape — `Periphery.Serial` as a thin abstraction with swappable `.Bcl` / `.RJCP` backends rather than the from-scratch native P/Invoke stack ADR-0028 planned, which it supersedes — but no `Periphery.Serial` package exists yet, so the STM32 USART, ESP32 and EFM8-UART families on the roadmap are decisions, not code.
- **Every GitHub Release now carries `treehopper-flash.exe` — one self-contained Windows binary that is both the GUI and the CLI.** No arguments opens the Avalonia window; `gui` opens it with the host's own flags; anything else (`list`, `flash`, `autoflash`, …) runs the command line and attaches to the launching terminal. It is one binary rather than two, because two self-contained ~80–100 MB deployments pay for the .NET runtime twice. It is the branded composition of a much larger in-repo application that is **deliberately not on the package feed**: `Periphery.FlashAnything` (a pure MVU core plus an imperative service over the `Periphery.Bootloader` contract — watcher-driven discovery through a `MultiDeviceTracker`, bounded-parallel fleet flashing, and an **autoflash** mode that arms a family and flashes boards as they are plugged in, gated by a pure `AutoflashPolicy` that refuses probe-identified families and never flashes the same device twice in a session), its CLI and GUI toolkit libraries, and `Periphery.Bootloader.Stm32.Usb` (ST AN3156 USB DFU: pure DFU 1.1 + ST-command core, control transfers over `Periphery.Usb`, read-back verify via `DFU_UPLOAD`, validated end-to-end on real STM32G431 boards) all carry `<IsPackable>false</IsPackable>` while the platform is in progress, so `dotnet pack` does not produce them and no consumer can bind to a surface that is still moving. Build them from the repo if you need them today. The packages that **do** ship from this work are exactly four: `Periphery.Firmware`, `Periphery.Bootloader`, `Periphery.Bootloader.Efm8.Usb`, and `Periphery.Treehopper.Firmware`.
- **`DeviceFilter` is publicly constructible and directly evaluable** — `public DeviceFilter()` and `public bool Matches(DeviceInfo)` were both internal, so a filter could only ever be handed *to* Periphery's own query/watch builders, never built and evaluated by a consumer. ADR-0063 needs the opposite direction: `IBootloaderEntry.ExpectedBootloader` is a single filter value that both seeds the watcher waiting for a re-enumerated bootloader and serves as the safety gate refusing everything else, which requires constructing and matching one from outside the `Periphery` assembly. Widening only, no behaviour change — but it makes `DeviceFilter` usable as a standalone predicate over `DeviceInfo` by anyone who wants one.

### Changed
- **The `Periphery.Monitor` value contract is now platform-neutral by definition — and this deliberately breaks what three of its values *mean*, without changing a single byte of what they return** (ADR-0064, extending/partially superseding ADR-0059 and ADR-0058 D7). ADR-0059 claimed `MonitorLayout` / `MonitorLayoutEntry` / `MonitorConfiguration` were "platform-neutral on their face"; the *shape* was, but the **values crossing the seam baked in Windows CCD semantics with no X11/Wayland analog** — which downstream consumers compile against, so a future Linux backend could not have dropped in behind them without a breaking rework later. Three contract points changed meaning: (1) **`IsPrimary` is an explicit modeled flag a backend asserts, no longer the predicate "position == (0,0)"** — a consumer must not infer primary from coordinates, nor origin from primary (X11 has a real `primary` output flag unrelated to coordinates; a compositor may have no primary concept at all and report every entry `false`). (2) **`MonitorOrientation` is a semantic rotation (0°/90°/180°/270°), no longer the Windows `DMDO_*` ordinal it coincidentally matched** — its numeric values are now an opaque, stable serialization contract, and **no code may treat the ordinal as an OS rotation value**; every Windows translation is centralized in the new `Periphery.Monitor.Windows.CcdOrientation` (DEVMODE ordinal, and CCD rotation = ordinal + 1), which is also the only place a renumbering would have to touch. Reflection (X11 `RR_Reflect_*`, Wayland `*_FLIPPED_*`) is a **named gap**, not silently folded into the four rotations — surfacing it will be an explicit contract extension. (3) **`DisplayPosition` and the apply-side `Position` / `IsPrimary` axes are documented backend *capabilities*, not universal facts** — Wayland clients cannot set output position and have no readable global origin, so treat absolute cross-monitor geometry as meaningful only where the active backend documents a global desktop space, and expect a non-Windows applier to reject or ignore an unsupported axis explicitly rather than emulate it. **No behaviour changed** (the enum values are unaltered and `CcdOrientation` reproduces the former arithmetic exactly, so the CCD read/apply path is byte-for-byte identical) — this is a change to what a consumer is *entitled to assume*, which is why it is called out here rather than left to the ADR. No Linux backend was built; the point is that the types now already mean the right thing when one is.
- **`MonitorLayoutEntry.CurrentMode` is pinned to the panel's native (unrotated) frame, and that convention is now documented rather than accidental.** It was always read straight from the CCD source mode — so a portrait-mounted 1280×720 panel reads `1280×720`, not the desktop's `720×1280` — but the doc claimed "current orientation's frame", contradicting the code. With the contract ambiguous, every consumer re-derived the desktop footprint by guessing and they disagreed: the "-312 vs -56" position bug and a transposed remote-view crop are both that ambiguity. `CurrentMode` is now explicitly the native/source pixel mode, the **same frame as `PreferredMode` and `SupportedModes`**, so drift detection and mode-set validation compare like-for-like; `DisplayMode`'s own doc is frame-neutral (frame is a property of the field, not the type); and the desktop footprint has one place to come from — the new `MonitorLayoutEntry.DesktopSize` (see **Added**). A consumer that was reading `CurrentMode` as the desktop footprint was already wrong on rotated panels and should move to `DesktopSize`. Pinned end-to-end by a conformance test on a rotated panel (native 1280×720 portrait → `CurrentMode` 1280×720, `DesktopSize` 720×1280); the read frame was verified on real portrait hardware.
- **`Periphery.Efm8Bootloader` no longer exists — the package id is `Periphery.Bootloader.Efm8.Usb`, and the package is now a flasher rather than just an uploader** (ADR-0061 DEC-002, ADR-0063 slice 2). This is a **package-identity change, not an alias**: the old id is dead and will not be published again, so a consumer on it must update the `PackageReference` *and* the `using` — all fourteen types moved namespace with the package, though their names keep their `Efm8` prefix, so the namespace line is usually the whole edit. The rename itself changed no behaviour: the boot-record protocol, the record-replay uploader, and the reset-vector-written-last brick-safety are untouched. The reason is that the EFM8 uploader stopped being a one-off. ADR-0061's taxonomy is `Periphery.Bootloader.{family}.{transport}`, where the transport leaf is what the *operator* sees (`.Usb`) rather than the USB class underneath — EFM8 is HID-class and STM32 is DFU-class, but both are "USB" to the person holding the board — and where "DFU" is reserved for the one place it is literally true: it is the USB Device Firmware Upgrade class (ST AN3156), not a generic word for firmware update, and five of the six families on the roadmap do not speak it. Naming the serial packages `*.Dfu.*.Serial` would have re-created the exact AN3155-vs-AN3156 confusion the platform exists to remove. Note that the intermediate transport-free `Periphery.Bootloader.Efm8` family core the ADR sketches was **not** created — there is no second EFM8 transport yet, so the whole package is `.Efm8.Usb`, and the split can happen when a UART sibling earns it. On top of the rename the package gained its platform role: `Efm8HidProgrammer : IFirmwareProgrammer` (accepting `Efm8BootRecords` only — the format gate), `Efm8UsbBootloaderProvider : IBootloaderProvider` matching `0x10C4:0xEAC9`, and `Efm8IntelHexConverter`. One field fix rode along: `CanHandle` matched on VID/PID alone, but a USB-HID device enumerates on Windows as *two* nodes sharing that pair — the USB-bus parent and the HID-bus child — so the bootloader surfaced as two flashable targets in the GUI and one of them could not be opened as HID at all; it is now gated on `{ Category: Hid, BusType: HID }`, mirroring `HidBatteryEnricher`.
- **The Treehopper firmware-reflash surface left `Periphery.Treehopper` for a new published package, `Periphery.Treehopper.Firmware`** (ADR-0063 DEC-007). Breaking for anyone calling `TreehopperFirmwareUpdate`, `TreehopperReflashOptions`, `TreehopperReflashResult` or `TreehopperBootloaderEntry`: add the package reference and change the namespace to `Periphery.Treehopper.Firmware`. Everyone else gets a strictly smaller dependency graph, which is the entire point. `Periphery.Treehopper` is the *board* API — GPIO, I²C, SPI, LED, meters — but it carried reflash inline, so its package dependencies dragged `Periphery.Bootloader`, `Periphery.Bootloader.Efm8.Usb` and `Periphery.Hid` (and transitively `Periphery.Firmware`) onto every board consumer. a downstream kiosk consumes `Periphery.Treehopper` as a NuGet package to drive one LED strip and was inheriting four firmware packages it never calls. `Periphery.Treehopper`'s only Periphery dependencies are now `Periphery` and `Periphery.Usb`, and its build output ships zero bootloader, EFM8, HID or firmware assemblies. The board keeps `TreehopperBoard.RebootIntoBootloaderAsync` — that is board protocol, not flashing — and the new package composes it with the shared entry orchestration and the generic EFM8 flasher. Board-only consumers need no code change; they stop pulling the chain on the next `Periphery.Treehopper` republish.
- **`DeviceInfo.Id` is a `DeviceId` value, not a `string`** (and `DeviceInfo.ParentId` is a `DeviceId?`). The entity key threaded through every subsystem was the only raw string among the typed values — `HardwareId`, `SerialPortName` and `UsbClassCode` were already record structs — and the case-insensitive instance-id identity invariant rode on every keyer *remembering* to route through a static helper. A plain string compare silently reintroduced the phantom-duplicate bug that helper's own doc-comment warned about. The invariant now lives in the value: `Equals`, `GetHashCode` and `==`/`!=` are hand-written to `OrdinalIgnoreCase` (a record struct's synthesized equality is case-sensitive), so dictionaries and sets keyed by `DeviceId` are case-insensitive with no per-call-site comparer, and the tracker, watcher and multi-device host key on it directly. `WithParent` and the `ParentId` diff now compare case-insensitively too — parent ids are themselves instance ids, and that comparison was latently case-sensitive. Migration is mostly free: implicit conversions in both directions mean only call sites doing string operations on the raw id (`.StartsWith`, `.Length`) need an edit, and **the JSON wire format is unchanged** — `DeviceIdJsonConverter` reads and writes a bare string, not an object. One behavioural sharpening: a `DeviceInfo` can no longer be constructed with a null or empty `Id`, because the typed value rejects it at construction rather than at a later boundary check.

### Removed
- **`CameraConfiguration.DropLateFrames` and `CameraSessionBuilder.DropLateFrames(bool)` are gone — they never did anything.** The option was declared, settable, and covered by a test that asserted it round-tripped into the configuration, and its documentation promised late-frame back-pressure ("pass `false` to back-pressure the producer instead") — but no code in `CameraSession` or the producer loop ever *read* it. Late-frame behaviour has always been governed entirely by the orthogonal `BufferExhaustionPolicy` (`DropIncoming` / `DropOldestQueued` / `BlockProducer` / `AllocateOverflow`), which is the only knob `DeliverFrameAsync` switches on. It was deleted rather than wired up, because wiring it would produce two overlapping late-frame knobs with undefined interaction (what does `DropLateFrames = true` plus `BlockProducer` mean?) — strictly worse than the single policy that already works. `BufferExhaustionPolicy` is now the one late-frame knob; a consumer that was setting `DropLateFrames` was already getting no effect from it and should express the intent there.

### Fixed
- **`MonitorLayout` no longer reports more than one primary monitor in clone/duplicate mode, and no longer hands the primary flag to a virtual display parked at the origin.** `CcdLayout` inferred `IsPrimary` purely from source position == (0,0). In clone mode several active paths share one source at the origin, so **multiple entries came back `IsPrimary = true`** — `MonitorLayoutApplier` throws on `Count(IsPrimary) > 1`, so the fleet station agent's converger simply never converged; an IddCx virtual display parked at the origin was mis-flagged the same way and stole the station intrinsic. The shell now reads the authoritative GDI primary source name (`MONITORINFOF_PRIMARY`, which Windows sets on exactly one monitor) and the decision is a pure `MonitorPrimary.SelectPrimaryIndex` over already-parsed path facts: match the GDI primary source (first-wins, which collapses clone paths sharing that source), falling back to the (0,0) origin only when the GDI read is unavailable. Returning a single index makes two primaries **structurally impossible** rather than merely unlikely. Clones stay one entry per active path with exactly one primary — marked, not collapsed — so each monitor keeps its identity for the applier.
- **The apply path now speaks the same native-frame `CurrentMode` convention as the read path, so a rotated panel can actually be satisfied.** Pinning the read model (above) left the same misconception on the write side: `MonitorConfiguration.Mode` was documented in the transposed final-orientation frame, so `LayoutDiff.IsSatisfiedBy` — which compares `config.Mode` against the now-native `CurrentMode` — **could never be satisfied for a portrait panel, and the converger would thrash forever**; and `CcdLayoutApplier` swapped the CCD source width/height when a rotation crossed the landscape/portrait boundary, which is wrong (a native 1920×1080 surface rotated 90° displays as a 1080×1920 desktop because the OS derives the footprint from source + rotation — the source stays native). **Contract change for apply-side callers:** `MonitorConfiguration.Mode` is the native frame, matching `CurrentMode`; the applier sets only `TargetInfo.Rotation` and writes the source dimensions verbatim, never transposed. ADR-0059's "rotation swaps the source frame" decision is corrected. Six pure `LayoutDiff` cases pin it (a portrait panel is satisfied by its native 1920×1080 and explicitly *not* by the transposed 1080×1920). Known limit, stated plainly: the read frame was verified on real portrait hardware, but the apply-side source frame at `SetDisplayConfig` time is derived from that same invariant and has **not** itself been exercised on hardware that actively rotates a panel — the fail-loud post-verify is the backstop, and the physical rotation round-trip should be confirmed before relying on active rotation.
- **Treehopper firmware v2.75 — a board no longer wedges mid-SPI and stops answering USB until it is unplugged.** Boards in the field stopped responding partway through an SPI burst, and the failure was blamed on EFM8 silicon. It is not silicon; it is a firmware timing race, and the investigation is in `docs/investigations/2026-06-treehopper-spi-usb-lockup.md`. A USB interrupt firing during the polled SPI FIFO service lets the RX FIFO overflow and drop bytes, which desyncs the poll loop's counters into an infinite spin — hence the narrow ~4–5 MHz band, the scaling with transfer length, and the Heisenbug behaviour where instrumenting the loop makes it disappear. The fix services the FIFO loop in short windows with interrupts masked, reopening between windows so USB is never starved, and caps TX feeding at the window size so the SPI is idle at every unmask boundary (a first cut that drained via `while(SPIBSY)` without reading RX overflowed the RX FIFO *during the drain* and hung on transfer #0). The window is sized from the live SPI clock divider so the masked period stays under ~256 µs across the whole 94 kHz – 12 MHz range rather than imposing a minimum-SPI-frequency floor — slow SPI is a real requirement for long or breadboard wiring, slow/isolated slaves, and bring-up. A second, independent bug is fixed with it: `SPI0CKR` was being written on the wrong SFR page (`0x00` instead of `0x20`), so it was silently ignored and the host's requested clock was **never actually applied**. Validated across 0.094 / 0.5 / 1 / 2 / 4 / 5 / 6 / 8 / 12 MHz under USB load (4 and 5 MHz wedged before the fix; the control case wedges within nine transfers), MOSI byte-perfect on a logic analyser, and 3,950 transfers clean in the 4 MHz / 200 B danger band on real hardware. The image fits under the EFM8UB1 `0x3A00` bootloader wall with ~25 bytes of headroom, which is why the build uses `OPTIMIZE(SIZE)`. `bcdDevice` is bumped `0x0112 → 0x0113` so the host updater's version gate will flash it over a 2.74 board; the built `.hex` and the boot-record `.tfi` are committed under `src/Periphery.Treehopper/firmware/Treehopper-EFM8/dist/`, and a release build of `Periphery.Treehopper.Control.Cli` embeds the `.tfi` via `-p:TreehopperFirmwareImage=`. Because the firmware is now preemption-safe across the full clock range, the host-side 0.8–6 MHz clamp can be retired.
- **A clean restore of `Periphery.Treehopper.Firmware` no longer fails with NU1101** (`#134`). `Periphery.Bootloader` was left `IsPackable=false` from its original stub scaffold, but it had since graduated into the real flashing-contract package that `Periphery.Bootloader.Efm8.Usb` implements and `Periphery.Treehopper.Firmware` references. The packed firmware `.nupkg` therefore declared a dependency on a package that was never published, so any consumer restoring it from the feed got `NU1101` — and the failure was invisible in-house, because the local development feed's `.nupkg` masked it on operator boxes. It is packable now, closing the chain; its own dependencies (`Periphery`, `Periphery.Firmware`) were already published.
- **Planar camera formats no longer double-allocate the frame pool.** Bytes-per-pixel, row stride, frame size and plane count for `CameraPixelFormat` were computed by ad-hoc `switch` expressions copy-pasted across `CameraSession`, `CameraFramePool`, `MfCameraBackend` and the benchmark backend, and the copies had drifted. The worst drift: `CameraSession.EstimateFrameSize` charged NV12 / NV21 / I420 / YV12 at 3 bytes per pixel, when 4:2:0 chroma subsampling is 12 bits per pixel — 1.5 bytes — so every planar-format pool was seeded at twice the size it needed. All four copies are deleted in favour of one pure `CameraFrameLayout` (`BitsPerPixel`, `BytesPerRow`, `FrameSize`, `PlaneCount`); it is expressed in *bits* per pixel precisely so the 4:2:0 cost stays exact rather than rounding to a wrong whole number. Wasteful rather than dangerous — nothing downstream depended on the larger buffer — but it is now a directly unit-tested function instead of four hand-copied switches.
- **A quick `StartAsync` → `DisposeAsync` on the Linux monitor provider no longer throws a spurious `TaskCanceledException`.** `LinuxDeviceMonitorProvider.StartAsync` scheduled its udev poll loop with the monitor's own cancellation token passed as `Task.Factory.StartNew`'s *creation* token. That tells the TPL to cancel the task before the delegate ever runs if the token is already signalled — so any fast start-then-dispose (which is every `await using` lifecycle path, including the contract tests) transitioned the task straight to `Canceled`, and `DisposeAsync` then awaited a pre-cancelled task and surfaced the exception from teardown. This was the intermittent red on the Linux CI runner (`LinuxDeviceMonitorProviderContractTests.StartAsync_FirstCall_DoesNotThrow` failing, then passing on a plain re-run of the identical commit). Scheduling now uses `CancellationToken.None`: cancellation is the loop's job, not the scheduler's, and the loop already observes the token in its `while` condition, so on a quick dispose it starts, sees the cancelled token, skips the body and returns normally. Reproduced under the CI container image (`mcr.microsoft.com/dotnet/sdk:10.0`) with an amplified start/dispose stress harness and then run 4,800 cycles clean with no defensive `catch` in place — the race is eliminated at the source rather than masked.

CI's Linux `build-test` job runs in the `mcr.microsoft.com/dotnet/sdk:10.0` container, which ships no .NET 8 runtime, so every `net8.0` testhost failed to launch and CI had been red repo-wide since 2026-07-11. - A whole-codebase architecture-deepening review (`docs/explorations/architecture-deepening-review-2026-06.md`) was actioned across PRs `#27`–`#38` — all ten Strong findings plus the typed-`DeviceId` and benchmark pixel-math items in `#27`–`#33` and `#35`, with the logging consolidation following in `#38`. The through-line is the functional-core / imperative-shell split the repo had adopted in principle but not everywhere: `DeviceTracker`'s per-profile latch and resolve logic became a pure immutable `DeviceTrackerResolution` with total transitions (the tracker keeps only the lock, one state cell and the notification shell); `IRecoveryPolicy.DecideAsync` became a synchronous, total `Decide` — the backoff curve it computed was always pure, and it was being forced into an async signature it never awaited — leaving the proxy shell to own the single `Task.Delay` the directive asks for; the reset-escalation *decision* split out of the reset IO into a pure `ResetEscalation.Decide`; the fixed 18-byte USB device-descriptor decode was lifted out of both the WinUSB and libusb shells into a pure `UsbDescriptors` parser with golden-vector tests, mirroring the HID report-descriptor exemplar; `CameraSession`'s frame timeout, elapsed measurement and bounded-stop waits moved onto an injectable `TimeProvider`, so the timeout-versus-cancellation decision is exercised with `FakeTimeProvider` instead of real timers; and the CLI's verbose device tree split into a pure `DeviceFieldProjection` plus a trivial Spectre rendering shell, giving that logic tests for the first time. One genuine purity leak in the repo's own exemplar was closed: the Treehopper SPI codec read the `TREEHOPPER_SPI_DANGER_BAND` environment variable on the pure encode path — a syscall per SPI transfer inside a function ADR-0052 declares total and side-effect-free — and the read moved to the board shell, which stamps the resulting flag onto each command. Separately, three near-identical copies of a file/console `ILoggerProvider` (the FlashAnything GUI host, a Treehopper example, and the CLI's console variant) collapsed into a new `Periphery.Diagnostics` project shaped as one provider behind an `ILogSink`; it is `IsPackable=false` — host scaffolding behind the `PeripheryLoggerFactory` seam, not library surface — so it never reaches the feed. All of these are behaviour-preserving by construction; the point was to make the decisions testable as values.

## 1.6.0-alpha.1 - 2026-06-16

### Added
- **`DeviceProxyBase` faulted-node recovery — self-heal a devnode that enumerates faulted and never reaches Active** (ADR-0060 Decision 11). The recovery ladder (retry → reset → `GaveUp`) previously had only one entry point: a session failed to *open* on a device the tracker reports as `Active`. A device that enumerates in an OS fault state (`DeviceStatus.Error`, e.g. Windows `CM_PROB_*` problem code 21 pending-removal / 10 failed-start / 31 driver-failed / 43 reported-problem) but never reaches `Active` maps to the tracker's `Present` bucket — the same bucket as a healthy paired-but-out-of-range Bluetooth device — so the proxy never attempted an open, the ladder never ran, and the node sat dead until an external disable/enable (the second the field unit incident: a Treehopper LED board dead from boot for 45+ minutes, cleared only by a manual `Disable-PnpDevice` / `Enable-PnpDevice`). A new, symmetric trigger drives the existing no-open-handle reset rungs (`PnpDisableEnable`, `UsbPortCycle`) against such a node after a short settle window (default 3s, to let a node that is merely mid driver-bring-up reach `Active` on its own first), routed through the same `IRecoveryPolicy`, the same reset budget / escalation / stable-open dwell, so a node that keeps re-faulting converges to `GaveUp` instead of reset-looping. Which nodes are eligible is decided by a pure, total classifier (`DeviceFaultClassifier.IsResettableFault`): `DeviceStatus.Error` is the cross-platform signal, and the Windows `RawStatus` problem code is used only to *exclude* — a user/policy-disabled node (`DeviceStatus.Disabled` or `CM_PROB_DISABLED` = 22) is **never** auto-enabled, and a node the OS reports as problem-free (code 0) is left alone. `RecoveryContext` gains a `Trigger` discriminator (`OpenFailure` | `EnumeratedFault`) so a policy can tell the two recovery causes apart. The trigger is **opt-in** via a new `faultedNodeRecovery` flag (default `false`) on `DeviceProxyBase` and forwarded through `DeviceProxy` / `DeviceProxy<T>` / `DeviceSessionHost` / `MultiDeviceSessionHost`; with the flag off — the default for every existing consumer — `OnTrackerStateChanged` behavior is unchanged (the proxy only ever acts on an `Active` device).
- **`Periphery.Treehopper.TreehopperDeviceReset`** — an `IDeviceReset` decorator that supplies the `ResetKind.SoftProtocol` rung core cannot (ADR-0060: a device-specific soft reset is owned by the device extension). For a Treehopper board it prepends a soft-reset strategy gentlest-first and executes it by opening the board and issuing `RebootAsync` (wire opcode `0x0C`, the port of the original SDK's `TreehopperUsb.Reboot()`); every other device and strategy delegate unchanged to the wrapped reset. Compose it on the OUTSIDE of any privileged/remote reset adapter so the soft rung runs locally (it is a board-protocol command, not a cfgmgr32 op). Rationale: the USB-level rungs (`UsbPortCycle`, `PnpDisableEnable`) only re-enumerate the host's view and cannot reset the board MCU firmware, so an EFM8 bulk-OUT firmware-endpoint wedge survives both (the board re-opens but the first SPI write re-faults); a firmware reboot over the still-live config endpoint can clear it, needs no elevation, and is the gentlest, so it leads the ladder.

### Fixed
- **`DeviceProxyBase` reset budget is now cleared on a stable-open dwell, not the instant open returns** (ADR-0060 Decision 10). The recovery ladder escalates over `ResetCount` (retry → reset strategies, gentlest first → `GaveUp`), but the budget was being zeroed the moment `OpenDeviceAsync` + `OnActivatedAsync` completed. A device whose OPEN succeeds (the open only exercises a healthy endpoint) but whose SESSION re-faults shortly after — the motivating case is a Treehopper LED board with a wedged DATA endpoint that opens via the healthy CONFIG endpoint, then faults ~2s later on the first SPI write — had its budget cleared before the refault, so every cycle restarted the ladder at strategy [0]: it never escalated, never reached `GaveUp` (so the "enumerated but unopenable; needs a human / power-cycle" signal never fired), and for a re-enumerating first strategy (e.g. a `SoftProtocol` board reboot) became a self-made infinite reset loop (reset → reopen → refault → reset, forever). The fix keeps `SetState(Open)` immediate (health / openability reporting stays correct at once) but defers clearing `ResetCount` / last-fault until the session survives a configurable `StableOpenDwell` (default 5s); a fault / close / reset / dispose before the dwell preserves the budget so the ladder keeps escalating and ultimately concedes. The dwell is keyed to the live connection generation and the per-connection cancellation token, so a stale timer never zeroes a newer connection's budget and nothing clears after disposal. The `OnTrackerStateChanged` re-enumeration clear (a genuine external replug from `GaveUp`) is kept and is orthogonal. This was the loop hazard gating a downstream Treehopper `SoftProtocol` reset rung.

## 1.5.1-alpha.1 - 2026-06-14

### Changed
- **`Periphery.Camera` Windows (Media Foundation) capture reuses its frame buffer** instead of allocating a fresh `byte[]` per frame. `MfCameraBackend` now backs every frame with one reusable buffer (grown only when the frame size increases) and slices `RawCameraFrame.Data` to the actual length, honouring the documented "valid only until the next `ReadRawFrameAsync`" contract the Linux V4l2 backend already relied on for its mmap mapping. At 30fps × 1280×720 BGRA32 this removes ~95-100 MB/s of large-object (LOH) allocation churn that was driving continuous gen2 GC. Field-validated on a deployed kiosk (Intel HD 620, .NET 10): steady-state allocation dropped ~97 MB/s → ~1.5 MB/s with no behavioural change (camera streams healthy, 0 frame exceptions).
